## ER-1 (2026-11-07, движок 1.3): код выхода при неизвестном ключе в /api

Контракт (`API_CONTRACT.md`, раздел «Ошибки»): «Ошибки аргументов
(неизвестный/неоднозначный ключ) — код 2».

Фактически — два разных поведения:

1. Латинский неизвестный ключ (`/zzz-no-such-key`): `resolve_option()` поднимает
   `SystemExit("Неизвестный ключ: …")` **до** установки `MACHINE`, поэтому JSON в
   stderr не формируется: код выхода **1**, в stderr — plain-текст.
2. Не-латинский ключ (`/zzz-ключ`): не подходит под регулярку ключей, уходит в
   argparse → код **2**, в stderr — usage-текст (тоже не JSON).

Для GUI не блокирует: обёртка показывает stderr при любом rc≠0. Предложение
(по усмотрению владельца): в режиме `/api` все ошибки аргументов оформлять
как stderr-JSON с кодом 2.

**СТАТУС: реализовано ZCode 2026-11-07 по решению владельца (раунд 3,
AGREEMENTS.md) — движок 1.4, ошибки аргументов = JSON stderr + код 2.**

## ER-2 (2026-11-07, движок 1.3): экспорт всех диалогов в один файл

GUI v2 имеет кнопку «Экспортировать всё в один файл» (пока неактивна).
Просьба: ключ вида `/single-file` — упаковать **все** диалоги в **один** файл
каждого формата (md/txt/json): диалоги идут подряд с заголовками-разделителями;
для JSON — объединённая структура (например, массив сессий). Конкретный формат
разделителей/структуры — на усмотрение владельца; GUI передаст только ключ +
`/format` + папку назначения.

**СТАТУС: реализовано ZCode 2026-11-07 по решению владельца — ключ
`/single-file` в обоих движках 1.4 (md/txt/json), пустые диалоги пропускаются.**

## ER-3 (2026-11-07, движок 1.3): BOM по-форматно

Сейчас `/no-bom` действует сразу на md **и** txt (all-or-nothing). GUI v2
показывает поформатную матрицу опций, поэтому чекбоксы BOM для md и txt
вынужденно синхронны. Предложение: разрешить раздельное управление, например
`/no-bom md|txt|all` (или эквивалент) — тогда GUI сможет передавать разные
значения для md и txt. До этого — синхронные чекбоксы + подсказка в GUI.

**СТАТУС: реализовано ZCode 2026-11-07 по решению владельца —
`/no-bom [md|txt|all]` в обоих движках 1.4 (в GUI чекбоксы md/ttx
синхронизированы, передача — по-форматно).**

## ER-4 (2026-11-07, движок 1.3): одинаковые опции для всех форматов вывода

Сейчас `/tools` и `/narration` влияют **только на md**: `render_text` (txt) и
`render_json` не принимают with_tools/with_narration — блоки инструментов и
промежуточные реплики в txt/json не попадают, какие бы ключи ни были заданы.
Просьба: сделать опции одинаковыми для всех форматов —
- txt: вызовы инструментов и реплики в текстовом виде (по аналогии с md);
- json: поля `tools` / `narration` в каждом turn.
Единственное оправданное исключение — BOM в json (технически невозможен).
GUI уже передаёт `/tools` и `/narration` для любого формата; после реализации
движка заработает без изменений GUI.

**СТАТУС: реализовано ZCode 2026-11-07 по решению владельца —
tools/narration в txt и json в обоих движках 1.4.**

## ER-5 (2026-11-07, движок 1.3): не перезаписывать существующие файлы

`build_filename` добавляет суффиксы `-2`, `-3` только внутри одного запуска
`/all` (локальный `used`); одиночный `/chat` и повторный `/all` молча
**перезаписывают** существующие файлы с тем же именем. Просьба: перед записью
проверять существование файла и добавлять порядковый суффикс вида
`(1)`, `(2)`, `(3)`… — единообразно для `/chat` и `/all` и между запусками.
Стиль суффикса — на усмотрение владельца; GUI показывает путь из JSON-ответа
и сам имена файлов не строит.

**СТАТУС: реализовано ZCode 2026-11-07 по решению владельца —
unique_path с суффиксами ` (1)`, ` (2)`… в обоих движках 1.4
(внутри `/all` сохранены и старые `-2`/`-3`, и новый механизм).**
